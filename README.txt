About the application
------------------------
Our application contains three main entities:

Department: Stores department information.
Employee: Stores employee information.
Course: Stores training course information.
====================================================

Relationship structure
-------------------------------
Department  1 -------- M  Employee

Employee    M -------- M  Course
                        |
                  employee_courses
                  (Association Table)

Understand Each Concept Through Execution
==========================================

Now let's examine the important examples and their expected results.

Example 1: One-to-Many Relationship
-----------------------------------
Enter: 2

Expected output:

--- EMPLOYEES BY DEPARTMENT ---
Department: Python
- Arun
- Priya

What happened?

This query loads the department:

department = session.scalar(
    select(Department).where(
        Department.department_name == "Python"
    )
)

The next operation accesses its employees:

department.employees

By default, the collection is lazily loaded.

    If the collection has not already been loaded, SQLAlchemy issues another SELECT to retrieve the employees.

    This demonstrates the difference between retrieving a department and retrieving its related employees.


Example 2: INNER JOIN
------------------------
Enter: 3

Expected output:

--- INNER JOIN ---
Arun -> Python
Priya -> Python
Karthik -> Java
Divya -> Testing

The query is:

statement = (
    select(
        Employee.employee_name,
        Department.department_name,
    )
    .join(Employee.department)
)


SQLAlchemy uses the relationship to determine the join condition.
The result contains selected values rather than complete ORM entities.
This is useful for reporting and summary endpoints.


Example 3: LEFT OUTER JOIN
----------------------------
Enter: 4

Expected output:

--- LEFT OUTER JOIN ---
Python -> Arun
Python -> Priya
Java -> Karthik
Testing -> Divya


In our current data, every department has at least one employee.

To demonstrate an unmatched row, add a department with no employees:

unused_department = Department(
    department_name="DevOps",
)

session.add(unused_department)
session.commit()

Then execute the LEFT JOIN again.

You will see:

DevOps -> None

Why?

    The LEFT OUTER JOIN preserves the department even though there is no matching employee.
    The employee_name result is None because the corresponding SQL column is NULL.
    This is one of the primary reasons for using a LEFT JOIN instead of an INNER JOIN.


Example 4: Many-to-Many Relationship
----------------------------------------
Enter: 6

Expected output:

--- EMPLOYEE COURSES ---
Employee: Arun
- Python Fundamentals
- SQLAlchemy ORM

The relevant query uses:

select(Employee).options(
    selectinload(Employee.courses)
)

SQLAlchemy retrieves Arun and then loads his associated courses through the association table.

The code does not manually query employee_courses.
    SQLAlchemy understands that Employee.courses uses that table.

Lazy Loading Versus Eager Loading
`````````````````````````````````````
This is the most important performance demonstration.

Lazy loading
`````````````````
Enter:  8

The code executes:

employee = session.scalar(
    select(Employee).where(
        Employee.employee_name == "Arun"
    )
)

This retrieves the employee.

Next:       employee.department.department_name

If the department relationship has not already been loaded, SQLAlchemy executes another query to retrieve it.


Conceptually, the SQL log resembles:

SELECT ...
FROM employees
WHERE employees.employee_name = 'Arun';

Followed by:

SELECT ...
FROM departments
WHERE departments.department_id = 1;

The second query occurs when the relationship is accessed.

This is lazy loading.


Eager loading with joinedload()   --> LEFT OUTER JOIN
``````````````````````````````````````
Enter: 9

The code executes:

statement = (
    select(Employee)
    .options(
        joinedload(Employee.department)
    )
)

The generated SQL typically uses a LEFT OUTER JOIN.

Conceptually:

SELECT
    employees.*,
    departments_1.*
FROM employees
LEFT OUTER JOIN departments AS departments_1
    ON departments_1.department_id =
       employees.department_id;

The department information is retrieved as part of the same query.

When the application accesses:

employee.department.department_name

SQLAlchemy does not need another SELECT for that already-loaded relationship.

This is eager loading.



Eager loading with selectinload()
-----------------------------------
Enter: 10

The query is:

statement = (
    select(Employee)
    .options(
        selectinload(Employee.courses)
    )
)


*** SQLAlchemy retrieves employees first.

*** Then it issues a second query, or additional batched queries if needed, to retrieve the courses associated with those employees.

Conceptually:

SELECT *
FROM employees;

Then:

SELECT ...
FROM employees
JOIN employee_courses
    ON employees.employee_id =
       employee_courses.employee_id
JOIN courses
    ON courses.course_id =
       employee_courses.course_id
WHERE employees.employee_id IN (...);


The exact generated SQL can differ, but the principle is that related collections are retrieved in batches rather than by issuing one query for every employee.


When should you choose each strategy?
-----------------------------------------
Situation	                                             Recommended starting point
Retrieve an employee and their department	             joinedload()
Retrieve departments and their employee collections	    selectinload()
Retrieve employees and their courses	                selectinload()
Retrieve only employee and department names	Explicit JOIN with column selection
Load related objects only when needed	Lazy loading
Prevent unexpected relationship queries	lazy="raise"
Part 11: Understand and Solve the N+1 Problem

Consider this code:

employees = session.scalars(
    select(Employee)
).all()

for employee in employees:
    print(
        employee.employee_name,
        employee.department.department_name,
    )

This code can generate:

One query to retrieve all employees.
Additional queries to load departments as needed.

If every employee belongs to a different department, the operation can approach 101 SELECT statements for 100 employees.

If several employees share the same department, the identity map may reduce the number of additional queries.

Nevertheless, repeated lazy loading can still create a performance problem.

Solution

Use:

statement = (
    select(Employee)
    .options(
        joinedload(Employee.department)
    )
)

For the department relationship, the eager-loading strategy avoids issuing a separate department query for each employee.

For courses, use:

statement = (
    select(Employee)
    .options(
        selectinload(Employee.courses)
    )
)

This retrieves the employees and their course collections using batched queries.

For both relationships:

statement = (
    select(Employee)
    .options(
        joinedload(Employee.department),
        selectinload(Employee.courses),
    )
)

This is the strategy used in menu option 11.

Training exercise: Compare the SQL logs for options 8, 9, 10, and 11. Count the SELECT statements and identify when each relationship is loaded.

Part 12: Additional JOIN Concepts

SQLAlchemy supports several additional query patterns worth introducing during training.

12.1 Filter using a related table

Find employees in the Python department:

statement = (
    select(Employee)
    .join(Employee.department)
    .where(
        Department.department_name == "Python"
    )
)

employees = session.scalars(statement).all()

Expected result:

Arun
Priya

The database filters the records instead of retrieving all employees and filtering them in Python.

12.2 JOIN through a many-to-many relationship

Find employees enrolled in SQLAlchemy ORM:

statement = (
    select(Employee)
    .join(Employee.courses)
    .where(
        Course.course_name == "SQLAlchemy ORM"
    )
)

employees = session.scalars(statement).all()

Expected result:

Arun
Karthik

SQLAlchemy understands that the relationship joins through the association table.

Conceptually:

Employee
   |
   v
employee_courses
   |
   v
Course
12.3 GROUP BY and COUNT

Count employees in each department:

statement = (
    select(
        Department.department_name,
        func.count(Employee.employee_id),
    )
    .outerjoin(Department.employees)
    .group_by(
        Department.department_id,
        Department.department_name,
    )
)

If the DevOps department was added earlier, the output includes:

Python -> 2
Java -> 1
Testing -> 1
DevOps -> 0

Why use outerjoin()?

It allows departments with zero employees to appear in the results.

Why use count(Employee.employee_id) instead of count(*)?

A LEFT JOIN produces a row for a department with no employee. COUNT(*) would count that joined row, whereas COUNT(Employee.employee_id) ignores the NULL employee ID and correctly returns zero.

Part 13: Important Related Concepts
13.1 Database cascades versus ORM cascades

The association table contains:

ForeignKey(
    "employees.employee_id",
    ondelete="CASCADE",
)

This configures a database-level foreign key action.

If an employee row is deleted, the database can remove its corresponding association rows.

This does not mean that all related courses should be deleted.

Courses are independent entities.

Deleting an employee should ordinarily remove their enrollment associations, not the courses themselves.

Also, PostgreSQL enforces the foreign-key action, whereas SQLite requires foreign-key enforcement to be enabled explicitly. If you run the same project with SQLite, configure and verify SQLite foreign-key enforcement before relying on ondelete="CASCADE".

For production applications, use migrations to manage schema changes rather than relying on create_all().

13.2 The Session and identity map

Consider:

employee1 = session.get(Employee, 101)

employee2 = session.get(Employee, 101)

print(employee1 is employee2)

Within the same session, the result is generally:

True

SQLAlchemy's identity map maintains one ORM object instance for a given database identity within the session.

However, the identity map is not a general query cache. A filtered SELECT may still execute even if matching objects are already present in the session.

13.3 Pagination

The project includes:

statement = (
    select(Employee)
    .order_by(Employee.employee_id)
    .offset(0)
    .limit(2)
)

This retrieves the first two employees.

For the next page:

page = 2
page_size = 2

offset_value = (page - 1) * page_size

statement = (
    select(Employee)
    .order_by(Employee.employee_id)
    .offset(offset_value)
    .limit(page_size)
)

Pagination is important because loading every record and all its relationships can consume excessive database resources and application memory.

For very large datasets, keyset pagination can be more efficient than large offsets.

13.4 Retrieve only the required columns

For a summary report:

statement = select(
    Employee.employee_id,
    Employee.employee_name,
)

This avoids loading complete employee ORM objects when the application only needs two columns.

For read-only reports, dashboards, and exports, selecting specific columns can be an effective optimization.

Part 14: Common Errors and Troubleshooting
Error 1: Connection refused

Check whether the PostgreSQL service is running.

Verify:

Host: localhost
Port: 5432
Database name: company_db
PostgreSQL service status
Error 2: Password authentication failed

Verify the credentials in .env.

Remember that URL.create() handles special characters in the password correctly.

Error 3: relation "employees" does not exist

Run:

python seed_data.py

Make sure you are connected to the correct database.

Error 4: Duplicate employee email

The database has:

email: Mapped[str] = mapped_column(
    String(150),
    unique=True,
    nullable=False,
)

PostgreSQL enforces the uniqueness constraint.

If you attempt to insert a duplicate email, the transaction fails. Roll back the session before attempting additional database operations.

Error 5: Relationship configuration error

Check that:

The foreign key references the correct table and column.
Both sides of a bidirectional relationship use matching back_populates names.
The association table is defined in the correct metadata.
All related models are imported before the mappings are first used.
Error 6: Too many queries

Enable SQL logging and inspect the generated SQL.

Look for repeated queries that load the same relationship for each record.

Consider selectinload() or joinedload() where appropriate.
